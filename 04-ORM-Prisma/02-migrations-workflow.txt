ORM (Prisma) 2 - Migrations Across Multiple Schema Changes
=============================================================

../12-prisma-orm.js only ever ran `prisma migrate dev --name init` once.
In a real project you run it every time schema.prisma changes:

  npx prisma migrate dev --name init            # creates User, Post
  npx prisma migrate dev --name add-tags         # later: adds Tag, PostTag
  npx prisma migrate dev --name add-comments     # later still: adds Comment

Each call:
  1. Diffs schema.prisma against the migration history.
  2. Generates a new timestamped folder under prisma/migrations/ with the
     raw SQL for just that change.
  3. Applies it to your dev database.
  4. Regenerates the Prisma Client so its types/methods match.

Migrations are committed to git - the migrations folder is a changelog of
your schema's entire history, replayable on any environment
(`prisma migrate deploy` in CI/production applies unapplied migrations
without prompting or generating new ones).

What happens with conflicting migrations from two developers
--------------------------------------------------------------
Both branch off the same schema state. Dev A adds Comment, runs
`migrate dev --name add-comments`, merges to main. Dev B, still on the
older schema, adds a `bio` field to User and runs
`migrate dev --name add-user-bio` locally BEFORE pulling Dev A's change.
When Dev B pulls main, Prisma notices the migration history diverged and
refuses to silently merge - it flags this rather than picking a winner.
Exactly like a git merge conflict, except the "file" is the sequence of
SQL migrations.

Fix: pull latest schema before branching new schema work off of it.

See Assignment 1 - Blog Platform/prisma/schema.prisma - its comment header
explains how that project's schema would land as two separate migrations
(init, then add-comments) in a real timeline, even though it's written as
one file you migrate once for convenience here.
