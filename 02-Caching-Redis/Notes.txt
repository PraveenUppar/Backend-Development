Topic 2: Caching / Redis - Key Concepts
=========================================

This assumes ..\10-caching.js is already covered - why caching helps, the
cache-aside pattern (check cache -> miss -> do the work -> store with a
TTL), cache invalidation on writes, and basic ioredis GET/SET. Redis is
way more than a key-value cache though - this folder is the hands-on deep
dive into the data structures and patterns that come up constantly in
real backends: leaderboards, sessions, rate limiting, and atomic counters.

Needs: Redis running locally for every file here -
  docker run -d -p 6379:6379 redis

The running example is a Realtime Utilities Service - the same three
patterns (rate limiting, sessions, leaderboard) that get built one at a
time across topics 1-3 below, then assembled into one service for the
assignment.

Sub-topics:
01-sorted-sets-leaderboard    - ZADD/ZINCRBY/ZRANGE for "top N" and
                                  "rank of X" without sorting anything
                                  yourself
02-session-storage            - Redis-backed sessions vs stateless JWTs,
                                  and TTL-based expiry
03-sliding-window-rate-limiter - ZADD + ZREMRANGEBYSCORE + ZCARD to rate
                                  limit without a boundary-burst loophole
04-atomic-incr                - INCR and why it beats read-then-write for
                                  counters under concurrency
05-key-expiration              - EXPIRE / PEXPIRE / TTL mechanics and the
                                  KEEPTTL gotcha

Why each matters (the 30-second version):
  - Sorted Sets   - a Sorted Set is a set of unique members where every
                     member also has a float "score", kept sorted
                     internally. Reading "top N" or "rank of X" is
                     log-time no matter how big the set gets - no query,
                     no in-memory sort. Works for leaderboards, trending
                     posts, most-active users - anything ranked by a
                     number.
  - Session
    storage       - JWTs are stateless: great for scaling, but you can't
                     revoke one early without extra machinery. A
                     server-side session in Redis flips that - the server
                     holds the truth, so logging a user out is just
                     deleting a key. Trade-off: a network hop to Redis on
                     every request vs in-process JWT verification.
  - Sliding-window
    rate limiter  - a fixed window ("max N per clock minute") lets a
                     client send N requests at :59 and another N at :00 -
                     2N in two seconds, both "within limits". A sliding
                     window looks at a rolling range of time ending NOW,
                     so there's no boundary to game.
  - Atomic INCR   - read-then-write (GET, add 1, SET) has a race: two
                     concurrent requests can both read the same value
                     before either writes, and one increment is silently
                     lost. Redis is single-threaded for command
                     execution, so INCR/HINCRBY/ZINCRBY can never
                     interleave with another client's command.
  - Key
    expiration    - TTL is what makes caches, sessions, and rate-limit
                     windows self-cleaning - no cron job sweeping stale
                     keys. Gotcha: a plain SET on an existing key clears
                     its TTL unless you pass KEEPTTL.

How to use this folder:
1. Go through 01 -> 05 in order - each file is a standalone Express app
   you can run against a local Redis and hit with the curl command in its
   header comment.
2. practice/ has 3 exercises that recombine these concepts on new
   scenarios (a trending-articles list, session-scoped request counters,
   and a login-attempt lockout).
3. Assignment 1 - Realtime Utilities Service/ assembles all of it into
   one service: sliding-window rate limiting on a demo route, Redis-
   backed login/me/logout, and a full leaderboard API. Read its
   README.txt for the brief, then the code.
