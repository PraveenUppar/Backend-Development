Topic 7: Testing APIs - Key Concepts
======================================

This assumes ..\15-testing-apis.js is already covered - the createApp()
factory pattern (so a test builds a fresh app instead of importing one
that's already listening on a port), supertest firing real HTTP requests
at that app in-process, and basic status/body assertions against a small
in-memory app. This folder covers what that one doesn't: the unit vs
integration distinction, spinning up a REAL throwaway MongoDB with
mongodb-memory-server, mocking an external SDK with jest.mock(), and
keeping tests from leaking data into each other.

Needs: jest, supertest, mongoose, mongodb-memory-server, and stripe as
devDependencies wherever you run these files (npm install them in this
folder, or run from inside the Assignment folder which already lists them).

Sub-topics:
01-unit-vs-integration      - a pure-function unit test next to an
                                HTTP-level integration test, so the
                                difference is concrete, not just definitions
02-mongodb-memory-server     - a real, disposable MongoDB per test run,
                                no Docker or shared dev database required
03-mocking-external-sdk      - jest.mock() to replace a third-party SDK
                                (Stripe) so tests never hit the real network
04-test-isolation             - afterEach cleanup so one test's leftover
                                data can't change the next test's results

Why each matters (the 30-second version):
  - Unit vs
    integration    - rule of thumb: if deleting the database and
                     hand-writing a fake in its place would still let the
                     test pass, it's a unit test (pure function, no I/O).
                     If the test only passes because something is
                     genuinely talking to a real server/database/API,
                     it's an integration test. Both matter - unit tests
                     are fast and pinpoint logic bugs; integration tests
                     catch the wiring bugs unit tests can't see.
  - mongodb-memory-
    server         - a mock database can't catch a bug in your actual
                     Mongoose query. mongodb-memory-server downloads a
                     real `mongod` binary once, then boots a real (if
                     disposable) MongoDB on a random port per test run -
                     real validation, real indexes, real transactions if
                     you opt into a MongoMemoryReplSet.
  - Mocking an
    external SDK   - you never want tests making real calls to a
                     third-party API: it needs real credentials, it's
                     slow, it can fail for reasons unrelated to your code,
                     and for something like Stripe it would create real
                     objects in a real account. jest.mock() replaces the
                     whole module for every file that requires it in that
                     test run, hoisted above even the require() calls.
  - Test isolation - tests in one file usually share expensive setup (one
                     mongod instance) for speed. Without cleanup between
                     tests, a document created in test 1 is still sitting
                     there when test 2 runs, silently changing counts and
                     query results out from under it. afterEach (not just
                     afterAll) means a failed test doesn't leave garbage
                     for the NEXT test to trip over.

How to use this folder:
1. Go through 01 -> 04 in order - each is a standalone Jest test file
   (npx jest 01-unit-vs-integration.js, etc.) you can run and read
   top to bottom like a lesson.
2. practice/ has 3 exercises that recombine these concepts (a second unit
   test for a validation helper, proving isolation breaks WITHOUT
   afterEach, and mocking a second SDK method).
3. Assignment 1 - Order Testing Suite/ separates the app from its tests
   the way a real project would (app.js + tests/orders.test.js instead of
   one file mixing both) and applies all four concepts together: a real
   Mongo-backed orders API, Stripe mocked out, and full isolation between
   tests. Read its README.txt for the brief, then the code.
