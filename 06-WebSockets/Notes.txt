Topic 6: WebSockets - Key Concepts
====================================

This assumes ..\14-websockets-socketio.js is already covered - why
WebSockets exist at all, the connection lifecycle, custom events, rooms
(join/leave/broadcast), and a JWT auth middleware sketch. This folder
covers the three things that actually bite you once a Socket.io app runs
for real, informed by the real project at Capstone 1 - Real-time Chat
API/ (server.js, rooms.js): reconnection semantics, scaling across
multiple instances, and testing Socket.io event handlers.

Sub-topics:
01-reconnection                - what survives a Socket.io reconnect and
                                  what doesn't (spoiler: room membership
                                  doesn't)
02-scaling-multi-instance       - why rooms silently break across more
                                  than one server instance, and how the
                                  Redis adapter fixes it
03-testing-websockets           - why supertest can't test Socket.io, and
                                  how socket.io-client + a real ephemeral
                                  server does

Why each matters (the 30-second version):
  - Reconnection   - Socket.io's client reconnects automatically, but
                     "reconnected" does not mean "picked up where it left
                     off." Losing the transport gives the client a BRAND
                     NEW socket.id; the server treats it as a fresh
                     connection, removes it from every room it was in,
                     and any state you attached directly to the socket
                     object is gone. The client must re-emit "join" on
                     every "connect" (which fires on reconnect too), not
                     just once at startup.
  - Scaling        - a socket is only "in a room" on the ONE process that
                     accepted its connection. Run two instances behind a
                     load balancer and `io.to("general").emit(...)` on
                     instance A never reaches a client connected to
                     instance B, even though both think they're in
                     "general." Sticky sessions alone don't fix this -
                     you need the @socket.io/redis-adapter so every
                     instance shares a pub/sub broadcast bus.
  - Testing        - supertest is built for one request -> one response;
                     a WebSocket is a long-lived, bidirectional event
                     stream, so there's no single response to assert on.
                     Test with the REAL socket.io-client library against
                     a real server on an ephemeral port - emit an event,
                     wait for the matching one back via done()/a Promise,
                     there's no in-memory fake the way supertest fakes HTTP.

How to use this folder:
1. Go through 01 -> 03 in order - 01 and 02 are runnable Socket.io
   servers you can connect to with socket.io-client; 03 is a Jest test
   file (npx jest 03-testing-websockets.js) that imports 01's server
   factory and drives it with real client connections.
2. practice/ has exercises that recombine these concepts (a reconnect
   handshake that restores room membership from the client side, running
   two instances locally to see rooms break without Redis, and writing a
   new test for the "typing" event).
3. Capstone 1 - Real-time Chat API/ is the full project these concepts
   were extracted from - REST endpoints alongside Socket.io, rooms with
   message history, typing indicators, and handshake-based auth. Read its
   README.txt for the brief, then the code.
